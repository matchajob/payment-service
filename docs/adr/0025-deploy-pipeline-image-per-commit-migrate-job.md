# ADR 0025: One image per commit, migrations as a Cloud Run Job before the service updates

**Status:** Accepted, 2026-11-17
**Slices:** 0.5, 16. **Fixes:** code-review-1 N4, N22. **Amends:** ADR 0012 (staging is applied by `app.yml`, not `infra.yml`).

## Decisions (Omer, 2026-11-17)

1. **`tsx` at runtime.** `@matcha/infra` ships as TypeScript and every import uses `@/` aliases, so plain `node` can't run `src/`. `tsx` moved to `dependencies`; the image installs production dependencies only and runs `node --import tsx src/api/server.ts`. A bundler (esbuild) was rejected for now: a build step, source maps and a hand-copied migrations folder, for a faster cold start we don't need yet.
2. **`drizzle/` is tracked, from one fresh baseline.** No deployed database existed, so the 12 local migrations were replaced by a single `0000` generated from today's DZD entities. Applying the old 12 and the new baseline to empty databases gave the same columns, types, defaults, constraints and indexes (`pg_dump --schema-only`, compared ignoring column order). Every later migration is generated by `db:generate`, never hand-written, and reviewed in its PR. CI runs `db:generate` and fails if it produces a file.
3. **Migrations run as a Cloud Run Job.** `payment-service-migrate` runs the same image with `src/cli/migrate.ts` (drizzle-orm's migrator, the one the test setup already uses), one task, no automatic retries, as the runtime account, with the same Cloud SQL mount and `DATABASE_URL` secret as the service. Rejected: migrating at server start (instances race, a slow migration fails the startup probe) and migrating from the CI runner (a TCP database URL and Cloud SQL access for the deployer).

## The pipeline (`.github/workflows/app.yml`)

- Every push: typecheck, lint, format, migration drift, tests against Postgres 17.
- `main`, once `GCP_PROJECT` is set on the `staging` environment: build the image tagged with the commit SHA and push it to Artifact Registry; `pulumi config set image`; `pulumi up --target` the migrate job; `gcloud run jobs execute payment-service-migrate --wait`; then `pulumi up` for everything else. New code never serves traffic against the old schema, as long as each migration is additive (expand first, remove in a later release).
- `infra.yml` only previews now. It sets `image` to the stack's `image` output first, so a preview never proposes rolling staging back to the placeholder image. Production stays applied by hand (ADR 0012).

## Consequences

- The first deploy needs the ADR 0012 bootstrap first: the migrate job's targeted `up` expects the database, the secrets and the runtime account to exist. Bootstrap adds two GitHub environment vars: `GCP_PROJECT` and `GCP_REGION`.
- Local builds forward one key: `docker build --ssh default=$HOME/.ssh/id_ed25519 .`. An agent holding a deploy key for another repo can offer that key first, and GitHub refuses it.
- Two `charges` foreign keys (`charges_subscription_connection`, `charges_payment_method_connection`) can no longer be the only one violated: `charges_card_of_subscription` (M13) and the `payment_methods` composite key overlap them, and which name Postgres reports depends on creation order, which the baseline changed. Their tests now assert rejection by any of the three.
